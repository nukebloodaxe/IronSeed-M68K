## 1. What we are porting [M]

| Item | Finding |
|---|---|
| Code | ~29 000 lines Turbo-Pascal-style Free Pascal (`-Mtp`, so `integer` = 16-bit), 27 units, plus **one C file (`c_utils.c`, 1 243 lines)** that is the entire platform layer |
| Platform layer | ~45 `cdecl external` functions: palette (`setrgb256`, `set256colors`), drawing primitives (line, circle, bar, pieslice, rectangle, `scale_img`, `upscroll`), mouse, keyboard (`readkey`, `key_pressed`), `delay`, MOD playback (`play_mod`, `haltmod`, `pausemod`, volume), sample playback (`play_sound`) |
| Display model | 320×200, **8-bit chunky**, VGA 256-colour palette. The game writes straight into a global `screen: array[0..199,0..319] of byte` (~600 direct `screen[]` accesses) and SDL copies it out from a separate thread |
| Colours actually used | Full-screen images use **29–239 colours, typically 60–140** (60 PNG sources measured) |
| Programs | Four executables chained with `exec`: `is` (launcher) → `intro`, `crewgen`, `main`. This was the DOS memory strategy and maps directly onto `Pexec` |
| Data | `data/` 2.5 MB (35 typed-record file types, `.cpr` compressed screens with palettes); music 28 ProTracker `.MOD` files, **4.6 MB total, 50–348 KB each**; 12 raw `.SAM` effects (120 KB) |
| Maths | 46 `real` declarations; `sin/cos/sqrt/arctan` in ~70 places; the planet renderer (`journey.pas` `makesphere*`, `intro.pas` `makeplanet`) does `real` arithmetic and `round()` **per pixel** |
| File formats | Typed files (`file of planarray` etc.) declared under `{$PACKRECORDS 1}`, written little-endian by DOS/x86 |
| Original requirements | 386/25 minimum, 486/33–50 with FPU recommended, VGA, ~530–615 KB conventional RAM, +1 MB EMS for sound |

**Headline:** the game is rewritten screen by screen in 68000 assembler (§3.1); the work is (1) a new platform layer, (2) 256→16 colours, (3) endianness/alignment of the data files, (4) making a 486-class game run on an 8 MHz 68000 with no FPU. Item 4 decides how good the result is; item 2 decides how it looks.

## 2. Target

- **Machine:** 1040STE with **4 MB (decided)**, TOS 1.62/2.06, hard disk (or Hatari GEMDOS drive). No 1 MB build.
- **Uses:** DMA sound, 4096-colour palette, blitter (all STEs have one [STE notes §1.8]). STF fallback is out of scope.
- **Mode:** take over the machine (no GEM), restore screen/palette/vectors on exit [expertise §14.8, §14.11].
- **Dev loop:** Hatari (STE, 4 MB, EmuTOS and real TOS 1.62) with its profiler; real hardware for timing and sound checks.

## 3. Key design decisions

### 3.1 Toolchain — pure 68000 assembler, one module per screen (decided)
Iron Seed is built from self-contained screens (bridge, star map, planet scan, comms, cargo, crew, combat, intro, crew generation, ending…) that share only a small global state: ship, crew, cargo, systems/planets, game date. That makes hand-written assembler practical:
- **Kernel** (resident): HAL — c2p + band LUTs, Timer B splits, VBL mixer, IKBD mouse/keys, `_hz_200` timing, file I/O, memory allocator, drawing primitives, text/font, `.cpr` decoder, fixed-point maths tables.
- **Global state block:** one structure; its offsets are **generated by a host script from the Pascal record declarations in `data.pas`**, so asm equates and the converted data files can't drift apart. Natural 68000 alignment, big-endian; the host converter writes the shipped data in that layout (this removes the packed-record question in §3.4).
- **Screen modules:** one source file per screen, entered and left through a fixed interface (enter, frame, input, leave), touching only the global block and kernel calls. Start as one PRG; split into Pexec-loaded overlays only if memory or build times demand it.
- **Register ABI** (written down before any module): d0–d2/a0–a2 scratch (as TOS [expertise §2.2]), d3–d7/a3–a6 preserved, a6 = global state base kept resident in every module.
- **Oracle testing:** instrument the Linux build to dump the global state (and the chunky screen) on entering/leaving each screen for a scripted input sequence; run the asm module in Hatari on the same inputs and compare dumps. A screen counts as ported only when the dumps match.
- Toolchain: **vasm 2.0f** (`vasmm68k_mot -Ftos -m68000 -devpac`, built from the GitHub mirror `mbitsnbites/vasm-mirror`), **Hatari 2.4.1** headless (STE, 4 MB, TOS 1.62 US ROM supplied by David), GEMDOS-emulated drive C:, `--auto` to start a PRG, debugger-script screenshots (`run_hatari.sh`).

### 3.2 Graphics: planar-first, chunky only where an algorithm needs it (revised from Phase 0)
Measured (§7): converting a whole chunky frame costs **475 ms**; comparing chunky against a previous copy costs **72 ms per frame even when nothing changed**. Both rule out a "chunky shadow converted every frame" design. Because the port is hand-written asm, the game no longer has to write chunky pixels at all:
- **Static pictures are converted offline** (host tool) to planar + per-band palettes, and drawn straight to the planar screen (blitter or `movem.l` copies).
- **UI primitives draw planar directly**: text, gauges, boxes, lines, icons — masked word writes per plane, as in [TY]'s span fill [expertise §11].
- **Chunky survives only for algorithms that are naturally per-pixel** (planet sphere wrap, scaled sprites, star fields, the comms "static"). They render into a chunky rectangle, **mark a dirty map** (one bit per 16-pixel group, one long per line) and the c2p converts only marked groups — cost is proportional to what changed, with no compare pass.
- c2p kernel: one LUT long per chunky value (4 plane bits in the 4 bytes), shift-accumulate 8 pixels, `MOVEP.L` the 4 plane bytes. ~48 cycles/pixel nominal; **verified pixel-exact** against a host model. LUTs are per band (§3.3).
- If the game logic ever reads pixels back (hit tests on `screen[]`), keep a chunky copy of just the affected regions, or replace the test with geometry.
- **Double buffer** the planar screen and swap on VBL [expertise §8.4].

### 3.3 Colour: 64 colours via raster split (decided)
Start with **four 16-colour bands per screen** (Frontier-style split), tuned up or down per screen once measured.
1. **Split tables per screen layout.** Each Iron Seed screen (bridge, star map, planet scan, comms, cargo, crew, combat, intro/ending pictures) gets up to 3 split scanlines plus 4 × 16 STE colours. Splits follow the layout's natural seams (viewscreen / panel / text box).
2. **Region-aware quantiser (host tool).** Quantise each band of each `.cpr` picture separately to 16 STE colours (12-bit, LSB in bit 3 [expertise §8.2]) and emit one 256→16 LUT **per band**. Reserve 3–4 slots in every band for the fixed UI colours (text, gauges, cursor) so they match across bands.
3. **c2p uses the band's LUT** for each line, so the chunky shadow stays unchanged.
4. **Split mechanics (measured, §7).** A naive Timer B handler finishes its palette write ~300 px into the first line of the new band — Timer B fires at the end of a line, and saving registers plus 16 colour writes takes longer than the ~192-cycle gap before the next line. Working scheme: **fire Timer B one line early**, preload the 16 colours into `d1-d7/a3`, **poll the video address counter** until it reaches the first byte of the split line, then `movem.l` all 16 colours at once; restart Timer B for the next band. Band 0 is loaded in the VBL. Cost ≈ up to one scanline of polling per split (~1 % CPU for 3 splits).
5. **Jitter (measured, §7).** With the [CG] recipe — wrap TOS's Timer C ($114) and ACIA ($118) handlers with `move.w #$2500,sr` so Timer B can preempt them — **4 500 of 4 500 splits** landed in the blank before their line, under DMA sound + mixer, IKBD packets every frame and c2p running flat out. Without the wrappers, 2.5 % were late. **No Timer A for sound** (Timer A outranks Timer B): DMA repeat mode over a ring buffer, mixed in the VBL (§3.5). Stop Timer B after the last band (a 4th interrupt otherwise fires at line 200).
6. **Fades:** scale all 4 × 16 hardware colours; no requantising.
7. **Mouse cursor** crosses splits; give it UI slots that are identical in every band.

### 3.4 Data files: endianness and alignment
- The DOS files are little-endian `{$PACKRECORDS 1}` records with words at odd offsets (e.g. `systemtype` starts with a 13-byte `string[12]`); a 68000 word access at an odd address is an address error [expertise §2.1].
- **Resolved by the asm route:** a host tool parses the record types in `data.pas`, emits (a) asm equates for a **naturally aligned, big-endian** layout, (b) a JSON layout used by (c) the converter that rewrites the shipped `data/*.dta` and by (d) the oracle comparator. Savegames are native big-endian on the ST.
- DOS packed sizes from the oracle dumps, for cross-checking the generator: `ship` 1 586 B, `systems` 6 750 B, `cargo` 3 625 B, `rescargo` 500 B, `events` 1 024 B, `logs` 512 B, `logpending` 512 B, `alien` 31 B, planets (`tempplan`) 33 000 B.
- `.cpr`, fonts and icon data are byte-oriented. **MOD files need no conversion** (big-endian headers already). `.SAM` effects: convert to **signed** 8-bit if unsigned (STE DMA is signed [PB-5 J.2]).
- Paths: 8.3 names already fit GEMDOS; savegames move into the game folder.

### 3.5 Sound
- **Music:** 4-channel MOD replay mixed to stereo in 68000 asm, streamed through DMA sound at **12 517 Hz** (25 kHz if CPU allows). Because of the raster split (§3.3), mixing runs in the **VBL**, not from Timer A: DMA repeat mode over a ring buffer sized in whole VBLs, refilled each VBL (frame registers are latched [PB-5 J.2]). The Timer A chaining recipe in [PB-5 J.2] is the fallback.
- **Effects:** mix `.SAM` samples into the same stream as a 5th voice (lasers, explosions), instead of stopping the music.
- **Volume:** LMC1992 master volume via Microwire for `setmodvolumeto` [later-machines §2.3].
- **Ring-buffer refill verified (§7):** the VBL reads the DMA frame counter and fills up to 8 bytes behind it (clear of the 4-word FIFO [PB-5 J.2]). It adapts to the frame rate by itself: 208.5 stereo pairs per VBL at 60 Hz = 12 517 Hz exactly.
- **Budget (measured, §7):** the naive sample-major mixer (4 voices, 8.8 phase with `lsr #8`) costs **~39 % of the CPU** at 12.5 kHz. Target ≤ 20 %: voice-major loops, `add/addx` fractional stepping (no shifts), unrolling, volume tables only where volume ≠ 64. Keep the rate configurable (6.25 kHz in combat if needed).
- Fallback: YM2149 music conversions — only if the mixer cost can't be afforded.

### 3.6 Input and timing
- **Mouse:** hook the IKBD relative-mouse packet via `Kbdvbase` [expertise §13]; keep our own x/y clamped to 320×200; draw the cursor in software into the planar screen (save/restore under), not via Line-A.
- **Keyboard:** `Bconin(2)` gives ASCII + scancode [expertise §5.3]; translate to the DOS `readkey` convention the game expects (0 then scancode for extended keys). Map ST scancodes to PC ones (they mostly match set 1; Help/Undo differ [expertise §13]).
- **Timing:** `delay(ms)` on `_hz_200` [expertise §4]; game speed must not depend on 50/60 Hz. **David's TOS 1.62 is the US ROM and boots at 60 Hz** (measured); NZ/PAL machines run 50 Hz. Everything VBL-related (mixer fill, cursor, splits) must work at both; consider forcing 50 Hz via $FF820A bit 1 for consistent timing on PAL displays.
- No threads: the SDL event thread becomes a VBL-queue routine (mouse cursor, flush, music housekeeping) [expertise §3.3].

### 3.7 Performance work (the long pole)
Guided by measurements (Hatari profiler, `_hz_200` timing in test PRGs):
1. Mixer to ≤ 20 % (§3.5); c2p only on dirty groups (§3.2).
2. Fixed point for every per-pixel/per-frame calculation: planet renderers (`makesphere*`, `makegasplanet`, `makestar`, `makeplanet`), star-map rotation (`info.pas rotateit`), combat. Sine tables ×16384 as in [TY] [expertise §11].
3. 64 000-byte temp-screen copies in the original become planar copies (32 000 bytes) with the blitter or `movem.l`.
4. Cache generated planet textures.
5. Watch interrupt latency: long instructions (`divs` ~158 cycles, big `movem`) in main code delay the split interrupt; the one-line-early scheme leaves ~500 cycles of margin.

### 3.8 Memory budget (4 MB target, rough)
TOS + basepages ~150 KB · program code (one of the four executables at a time) 200–400 KB? · c2p LUTs 4 KB per band set · chunky work areas only where needed · two planar screens 64 KB · game heap: temp screens (several × 64 KB), `backgr`, planet/system arrays ~0.5 MB · current MOD up to 348 KB + mix buffers. **Fits 4 MB comfortably; 1 MB needs streaming music and fewer temp screens.** Measure in Phase 2.

## 5. Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Volume of hand-written asm (~100k+ lines) | Time, session continuity | Per-screen modules; generated equates; written ABI; oracle diffs per screen |
| Raw speed (386/486 game on 8 MHz 68000) | Unplayable | Diff c2p, fixed point, asm hot spots; Mega STE 16 MHz as a "recommended" machine |
| Raster-split timing on real hardware | Wrong colours on the first pixels of a band | Measured in Hatari via the video counter; confirm with `SPLIT.PRG`/`JITTER.PRG` on David's STE |
| Mixer CPU cost (39 % naive) | Steals game time | Optimise to ≤ 20 %; configurable rate; YM fallback |
| Oracle runs are timing-dependent (real-time game, wall-clock input script) | Dumps differ for reasons other than bugs | Compare at screen entry/exit; add a deterministic-tick mode to the Linux build if needed |

### Sound cost (Phase 1, 14 Oct 2026)
The mixer and replay are bit-exact with `tools/modref.py`. Measured in Hatari (`tests/ktmix.s`): about **57 cycles per voice per output sample plus 38 per stereo pair** (the floor is ~44-52: one sample read, one volume-table read, one add, a 16.16 step).

| Song type | 12 517 Hz | 6 258 Hz |
|---|---|---|
| 4-channel (3 of 28 songs: GAME, CARGO, COMPONT) | ≈ 42 % CPU | ≈ 21 % |
| 6-channel (13 songs), all voices busy | ≈ 60 % | ≈ 30 % |
| 8-channel (12 songs), all voices busy | ≈ 80 % | ≈ 40 % |

Silent channels cost nothing (skipped), so real songs often sit below these numbers. `snd_mute` drops channels from the mix at no other cost. Options for David: (a) 6 258 Hz everywhere; (b) 12 517 Hz on menu/static screens, 6 258 Hz on real-time ones; (c) a per-song channel budget (mute the least important 2-4 channels of 6/8-channel songs during real-time screens); (d) offline 4-channel reductions of the 6/8-channel songs. Listening samples: `dist/*_12517Hz.wav` / `*_6258Hz.wav` (exactly what the STE mixes, before its analogue filter).

### Phase 2b (14 Oct 2026): the whole intro

### Phase 2c (15 Oct 2026): the port's own logo, credits, tidied title logo
- **Logo scene** (not in intro.pas; between 'Destiny: Virtual' and Mars): David's spinning logo (`assets/nblogo.gif`, 60 frames, 2 turns per second) turns above the sub-text "Nuke Bloodaxe M68K Ports", which arrives the way 'Destiny: Virtual' does (writestr2: converging from four directions with grey trails, then dothefade turns it red); wait(2), fading, Mars. ~9 s; a key skips to the title as everywhere else.
- `tools/mknblogo.py` → `DATA\NBLOGO.DAT` (529 KB): frames scaled to 137×110 with pixel aspect 1:1.2, 15 gold shades chosen as a brightness ramp and matched in a hue-weighted space (3-D clustering on the 4-bit grid gave olive/grey patches on the flat face), two bands (gold through palette entries 200-214 so the intro's fades work; main.pal 0-31 for the text below line 125), each frame a planar 160×110 box.
- Playback: a new kernel hook `vid_vbl_hook` copies the frame from the VBL, before the cursor and the mixer, straight into the shown screen. The copy (~380 cycles per line) is faster than the beam (512), so starting in the top border it never tears; if a VBL arrives late (beam less than 10 lines above the logo) that frame is skipped. One frame per VBL at 60 Hz, 1.2 at 50 Hz (the 200 Hz clock gave 0/1/2-frame steps, visibly jerky). Measured in Hatari with sound: 60 updates a second, 0 torn lines (debug build `ASMDEFS=-DNBDBG=1` counts them). Cost ≈ 32 % CPU during the scene; with INTRO1's 8 channels (≈ 45 %) the converge takes ~1.5 s (the PC's ~0.4 s).
- **Fast text for repeated strings:** `txt_mask` renders a string once into a 1-bit mask, `txt_mdraw` draws it flat and transparent with one shift per 16-pixel group (`tests/ktmask.s`: pixel-exact with `txt_print` over 28 cases incl. all shifts, both fonts, the band split, the right edge; ~4× faster even when rebuilding the mask every call). writestr2 uses it too: 'Destiny: Virtual' went from 7.7 s to 1.6 s.

How:
- **Virtual time** makes real-time loops comparable: the Linux build's delay() (IRONSEED_VTIME) and the ST's tim_delay (script line `vtime`) advance a virtual clock instead of waiting, and the scripts run on that clock (polls run them without advancing; a busy wait jumps to the end of the wait). Both sides then run each loop the same number of times between script events, so the clock, the planet's rotation and every random number line up. A Linux session takes under a second; the ST's ~1 minute in fast-forward Hatari.
- **FPC on x86-64 has two random overloads**: an arithmetic argument (random(ski+dif)) calls random(int64) (two 32-bit draws, 63 bits mod l), a variable or constant calls random(longint). Found by tracing the oracle with gdb when the crew's skill tests diverged; `mt_random64` reproduces it (tests/ktmt.s).
- **Screen model**: a chunky shadow of the whole screen with per-line dirty spans, flushed through the line LUTs (`gfx_c4_span`, ~45 cycles a pixel) where the original shows its drawing (mouseshow, delay). The bridge is 64 000 bytes of shadow plus a planar screen; the planet's 120x120 window is re-rendered (two half-renders in makesphere1/2, copied by makesphere3) every fourth main-loop frame; the game clock runs per frame like the original's, so game time per frame is the same.
- **Planet speed (measured in Hatari, 8 MHz, music on)**: one planet step every ~0.6 s (the original: every ~0.12 s, i.e. 4 loops of delay(tslice*3)); was ~1.1 s. Per step: u2_sphere_rows ~0.9 M cycles (table-driven now: `u2_shade` precomputes colour[alt][land] for the planet, a row pointer per index and the column offsets per frame, so the pixel loop is 3 lookups), flush ~0.9 M, mixer ~1.5 M. Arriving at a planet (readyplanet): ~14 s for the 3 walks of createplanet (was 47 s): the walk is inline with only the top word of the tempered MT number (exact fallback at the two threshold words), mt_update without calls, and a walk depends on the seed only, so the 2nd and 3rd calls replay the recorded steps (u2_walk, 75 000 bytes) and restore the generator state after it - pixel-exact with Linux. reloadbackground composes main over cloud by transparent runs (was ~1 s a call).
- **Bands**: LOG mode fitted on every log page, the title list, both light states and the cursor frames (pixel-exact preview with the original text); MAIN mode fitted on the bridge with 10 planet types, the status panel, the text box colours, all cube faces, the three light/button colours (weighted) and the approach screen. The status lights still come out orange instead of red: 16 colours per line are too few for the viewscreen band (planet greys + panel + lights).

How:
- **Software FPU** (`kernel/fp.s`): a stack of 12-byte extended values (sign/exponent word + 64-bit mantissa, x87 layout) with two rounding modes - `FSSE` rounds every result to 53 bits (FPC's SSE code for double expressions), `FX87` keeps 64 bits and rounds on store (expressions with non-double-exact literals such as 0.66, 0.049, 6.28 and anything with sin/cos/arctan go to the x87). add/sub/mul/div/sqrt/sin/cos/atan/round (banker's)/trunc/compare/str(r:w:d). The constants come from FPC itself (`tools/mkfpconst.py`, `tools/mkgconst.py` → build/fpconst.i, gconst.i). `tests/fptest.py` checks 8730 random cases against FPC (tools/fp/fpref.pas): bit-exact.
- Integer forms replace reals where they were proven equal on the host (graypal's grey, the gray-step fade, weird.pas's blast).
- **Integer width**: FPC evaluates integer expressions in native width, so `(x+z)*0.0006` with x, z up to 23 000 does not wrap; on the 68000 such sums must be done in longs before going to the FPU (the long range scan's dots showed it).
- c_utils.c's `bar` and `rectangle` exclude the far edge/corner; `pmac.i` macros (PXY, PRT, BAR, FADE, LINE, FLDG…) keep each Pascal line about one asm line.
